# Answer Pages

This directory contains answers to questions about the AkashaRender codebase. Answers are generated in response to user queries and saved when they provide valuable insights.

## Questions Answered

- **[Detailed Flow for Rendering a Single Page from vpath](./rendering-flow-from-vpath.md)**: Complete step-by-step walkthrough of the rendering process from virtual path lookup through document cache query, three-stage rendering (first render, layout, Mahabhuta), filesystem output, and performance tracking. Includes visual flow diagram, key data structures, special cases, and performance considerations.
- **[When Was Clinic Added as a Dependency, and How Would It Help AkashaRender?](./clinic-dependency.md)**: Finds that `clinic` was never a dependency in `package.json` (it is documented in `PROFILING.md` only as an optional global-install profiling tool) and explains how Clinic.js (doctor, flame, bubbleprof) would help diagnose performance bottlenecks in AkashaRender builds.
- **[Elements Required for ActivityPub and Fediverse Integration](./activitypub-fediverse-html-elements.md)**: Outlines what is actually required to make AkashaCMS content Fediverse-friendly. Clarifies that ActivityPub is a JSON-LD/HTTP protocol (not an HTML-tag standard), so the "HTML schema tags" are really Open Graph + Twitter Card + the Mastodon `fediverse:creator` convention. Presents a tiered/phased plugin design: Tier 1 `<head>` metadata, Tier 2 discovery endpoints (WebFinger, NodeInfo, host-meta), Tier 3 static ActivityPub actor/object JSON-LD, and Tier 4 live federation. Because shared hosting almost always provides **PHP**, the page details how small PHP scripts (WebFinger query handler with `.htaccess`, content-negotiating router, inbox, signed delivery) supply the dynamic shim, and explains the Actor / Collections / Objects-Activities entities in detail.
- **[Bluesky / AT Protocol Integration and Crossover with the Fediverse](./bluesky-atproto-integration.md)**: Explains that Bluesky (AT Protocol) and the Fediverse (ActivityPub) are separate networks that only cross over via bridges such as Bridgy Fed. Bluesky does not crawl a site for content; it fetches **Open Graph** tags for link-preview cards and, if the owner opts in, a **domain-handle verification** artifact. Recommends an AkashaCMS approach: reuse the shared Open Graph metadata, and optionally generate `/.well-known/atproto-did` (or document the `_atproto` DNS TXT record) so the domain can serve as the owner's Bluesky handle. Protocol-level federation is left to a bridge.
- **[Useful Microformats and IndieWeb Markup for a Static Blog](./microformats-indieweb-for-static-blogs.md)**: Summarizes the microformats worth implementing for a static blog (issue #33), recommending **microformats2** (`h-entry`, `h-card`, `h-feed`) over the classic v1 vocabulary. Covers the author-listing case as a nested `p-author h-card`, plus a representative `h-card` and `rel="me"` for IndieWeb identity, `p-category`/`rel="tag"` for tags, and optional Webmention reply/like properties. Explains that these are pure `class`/`rel` annotations on markup AkashaCMS already emits, so the work lives in partial templates and the blog/authors plugins and complements (not replaces) Open Graph.
- **[Social-Sharing Metadata: Open Graph, Twitter Cards, and Facebook](./social-sharing-metadata-opengraph-twitter-facebook.md)**: Describes the three link-preview vocabularies (Open Graph is primary; Facebook just consumes OG plus `fb:app_id`/`article:*`; Twitter Cards mostly fall back to OG), and the key `property=` vs `name=` distinction. Audits the current `@akashacms/plugins-base` implementation (`ak_headermeta` partials + `fixHeaderMeta`), finding real defects: `og:*` emitted with the wrong `name=` attribute, no Twitter Cards, weak Facebook/`article:*` support, latent `arg.pagetitle` bugs, and tests that encode the bug. Proposes an improvement: a frontmatter-driven `social:` block (with a generic `extra:` pass-through) normalized into a data table emitted by one template loop, with strong fallbacks so most pages need no extra frontmatter.
- **[Options for Storing Date/Time Values in the In-Memory SQLite Database](./sqlite-datetime-storage-options.md)**: Answers issue #120 — documents the two current conventions (epoch-millisecond numbers for the file-cache `mtimeMs`/`publicationTime` columns, ISO-8601 text for the TRACES table), clarifies that the `GENERATED ALWAYS AS (json_extract(...))` column is a JSON-extraction technique rather than a date format, surveys the five storage options (ISO-8601 TEXT, Julian day REAL, Unix epoch seconds, epoch milliseconds, sqlean `time` extension) with trade-offs, and recommends staying with epoch milliseconds given the all-JavaScript consumers; also flags a stale "seconds since 1970" comment in `schema.ts`.
- **[UNIQUE constraint failed: ASSETS.vpath (and DOCUMENTS.vpath) During Indexing](./unique-constraint-failed-assets-vpath.md)**: Explains why commands like `assetdirs`/`render` print many `Error gathering info for <vpath>: UNIQUE constraint failed: ASSETS.vpath` messages. The `VFStack` scan yields unique vpaths (deduped by its `#vpathMap`), and tables are created with `CREATE TABLE IF NOT EXISTS` but never truncated, so the collisions come from a **persistent database reused across runs** — i.e. `AK_DB_URL` pointing at a file instead of the default `:memory:`. Prior runs' rows survive and the fresh non-upsert `INSERT` collides on the `vpath` primary key. Fix: unset `AK_DB_URL` (or set it to `:memory:`), or start from an empty database file.
- **[Lightweight Image-Resize Packages to Replace sharp](./lightweight-image-resize-alternatives-to-sharp.md)**: Answers whether a small Node.js package can replace `sharp` for the built-in image-resize feature. Explains that sharp's size comes from bundled native libvips binaries, so only a **pure-JS or WASM** library reduces the install. Documents the tiny usage surface (load file, resize-to-width preserving aspect ratio, write with format chosen by destination extension — including the documented PNG→JPG conversion). SVG is out of scope (it is scaled via `width=`/`height=` attributes, not re-encoded). Compares **Jimp** (pure JS, drop-in, weak WebP), **photon-node**/**@cf-wasm/photon** and **Squoosh codecs** (WASM, real WebP/AVIF, lower-level API), and the **`@saschazar/wasm-*` monorepo** (one WASM package per format — `wasm-image-loader` decode+resize, `wasm-mozjpeg`/`wasm-webp`/`wasm-avif` encoders, plus EXIF/mean-color utilities — but buffer-based, no PNG encoder, ~5 years stale). Because WebP output is a goal, recommends a hybrid adapter (Jimp for JPEG/PNG + a maintained WASM WebP encoder) behind one internal module, and flags that the [Image Resizing](../concepts/image-resizing.md) concept page's "No Format Conversion" pitfall contradicts the built-in guide.
- **[Webmention: Purpose, Markup, Protocol, and Server Software](./webmention-protocol-and-markup.md)**: Explains Webmention as the W3C protocol for decentralized cross-site reply/like/repost notifications (the IndieWeb successor to Pingback). Covers the markup (a single `rel="webmention"` link to receive; microformats2 `u-in-reply-to`/`u-like-of`/`u-repost-of`/`h-card`/`e-content` to classify sent mentions), the full sending/receiving protocol (endpoint discovery, `POST` of `source`+`target`, and source-fetch verification), and the server-side options (hosted services like Webmention.io / webmention.app / Bridgy, or a self-hosted PHP receiver on shared hosting). Recommends an AkashaCMS approach: emit `rel="webmention"`, receive via a hosted endpoint, and fetch + render mentions at build time.
