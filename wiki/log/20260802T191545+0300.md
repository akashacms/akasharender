# 2026-08-02 19:15 - csv-table guide - document sync-vs-async parsing and future streaming

Added a "Sync vs async: why parsing is synchronous" subsection to the
`<csv-table>` implementation guide, prompted by a maintainer question about
whether reading/parsing should be asynchronous.

The subsection distinguishes the two operations: file **reading** is genuine I/O
and is async (`await fsp.readFile` in the custom element), while **parsing** the
already-in-memory string (`csv-parse/sync`, `jsyaml.load`, `parseTableData`) is
pure CPU work. It explains why synchronous parsing is correct here: the async
`csv-parse` entry point is a stream Transform whose asynchrony is about
back-pressure when piping a file stream (pointless once the whole file is in
memory); `async` does not make CPU-bound work non-blocking (only a worker thread
would, which is disproportionate for build-time author data); `js-yaml` has no
async load API; and keeping `parseTableData` synchronous makes it a pure,
easily-unit-testable function.

Also added a "Future work: streaming large files" note recording that, should
very large data files need support, the parse step should move to a streaming
pipeline (`fs.createReadStream` piped through the async stream-based `csv-parse`),
and documenting the templating-contract implications (the before-template's
`rowCount`/`columns` cannot be known before rows are emitted without a first
pass). Isolating parsing behind `parseTableData` keeps that future migration
contained. Added a matching entry to the Gotchas section and refreshed the page
`last-updated` timestamp.

This is a documentation-only change to the wiki; no source code was modified.
