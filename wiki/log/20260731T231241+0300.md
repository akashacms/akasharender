# 2026-07-31 23:12 - Drop SVG from sharp-alternatives answer; add @saschazar/wasm-* ecosystem detail

Follow-up to the previous answer page on lightweight image-resize alternatives
to `sharp`. The user clarified two points: (1) SVG should not be considered for
this task because SVG is a different kind of image, scaled in the browser via
`width=`/`height=` attributes rather than by recreating the file; and (2) they
wanted more detail on the `@saschazar/wasm-image` ecosystem, expecting it to be
a group of per-format packages plus useful operations.

## Analysis

- Researched the `saschazar21/webassembly` monorepo (npm scope
  `@saschazar/*`, MIT). Confirmed the user's expectation: it is a family of
  dependency-free WASM packages, roughly one per image format, plus utilities:
  - `wasm-image-loader` — decodes JPEG/PNG and resizes (stb_image / stb_image_resize)
  - `wasm-mozjpeg` — JPEG encoder (MozJPEG)
  - `wasm-webp` — WebP encode/decode (libwebp)
  - `wasm-avif` — AVIF encode/decode (dav1d)
  - `wasm-heif` — HEIF/HEIC decode
  - `wasm-exif` — EXIF reader
  - `wasm-mean-color` — mean/average color utility
- Key findings: the packages operate on **raw RGB(A) buffers, not files**,
  there is **no format-by-extension inference**, each ships a `.wasm` requiring
  manual `onRuntimeInitialized`, there is **no PNG encoder** in the set, and the
  monorepo was **last published ~5 years ago** (2020–2021) — effectively
  unmaintained.
