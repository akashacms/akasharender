# Breadcrumb Trail Schema.org Markup Architecture

## Query

Document the choice of web-schema (structured data) markup used for the breadcrumb trail generated by the `@akashacms/plugins-breadcrumbs` plugin. Explain why `BreadcrumbList` microdata was chosen, describe the JSON-LD alternative in full, and record that JSON-LD has *not* been implemented — mainly because JSON-LD `BreadcrumbList` markup requires absolute URLs, whereas AkashaCMS projects are rendered for relative URLs.

## Architecture

### 1. Background

The `@akashacms/plugins-breadcrumbs` plugin finds the series of `index.html` pages leading from a given document up to the site home page, and renders a trail of links to those `index.html` pages. This forms the breadcrumb navigation commonly placed at the top of a page.

The plugin renders the trail through a Nunjucks partial, `breadcrumb-trail.html.njk`, driven by the `doBreadcrumbTrail(metadata)` method (source: [../../../akashacms-breadcrumbs/index.mjs](../../../akashacms-breadcrumbs/index.mjs)). That method calls `akasha.indexChain(...)` to build the ordered list of crumbs, maps each entry to a `{ title, path }` object, and passes the list to the partial as the `breadcrumbs` variable. An equivalent EJS partial, `breadcrumb-trail.html.ejs`, is kept in sync for EJS-based sites.

The trail was already functional; the goal of this work was to add appropriate structured-data markup so search engines can recognize the breadcrumb trail.

### 2. Decision: schema.org `BreadcrumbList` Microdata

The plugin emits **schema.org `BreadcrumbList`** structured data expressed as **inline microdata** (`itemscope` / `itemtype` / `itemprop` attributes) on the existing HTML (source: [../../../akashacms-breadcrumbs/partials/breadcrumb-trail.html.njk](../../../akashacms-breadcrumbs/partials/breadcrumb-trail.html.njk)).

#### 2.1 Rendered markup

```njk
<div id="breadcrumbTrail" itemscope itemtype="https://schema.org/BreadcrumbList">
    {% for crumb in breadcrumbs %}
        <span itemprop="itemListElement" itemscope itemtype="https://schema.org/ListItem">
            &raquo; <a itemprop="item" href="{{ crumb.path }}"><span itemprop="name">{{ crumb.title }}</span></a>
            <meta itemprop="position" content="{{ loop.index }}" />
        </span>
    {% endfor %}
</div>
```

Structure of the emitted markup:

- The outer `<div id="breadcrumbTrail">` is the `BreadcrumbList` (`itemscope itemtype="https://schema.org/BreadcrumbList"`).
- Each crumb is wrapped in a `<span>` that is an `itemprop="itemListElement"` of type `ListItem`.
- Inside each `ListItem`:
  - The `<a itemprop="item">` supplies the URL of the crumb (its `href`).
  - The nested `<span itemprop="name">` supplies the human-readable label.
  - A `<meta itemprop="position">` supplies the 1-based position, taken from the Nunjucks `loop.index` (which is 1-based, exactly what schema.org requires).

The EJS partial produces the same structure, tracking position with a manual counter because EJS has no `loop.index` equivalent (source: [../../../akashacms-breadcrumbs/partials/breadcrumb-trail.html.ejs](../../../akashacms-breadcrumbs/partials/breadcrumb-trail.html.ejs)).

#### 2.2 Why microdata, and why `BreadcrumbList`

- **`BreadcrumbList` is the correct vocabulary for breadcrumbs.** Both Google and Bing document and consume schema.org `BreadcrumbList` for breadcrumb rich results. It is the standard, search-engine-recognized way to describe a breadcrumb trail.
- **Inline microdata reuses the existing DOM.** The `itemscope`/`itemprop` attributes attach to the anchors and list items that the trail already renders. There is no separate data block to keep synchronized with the visible markup, and the plugin's existing data flow (`indexChain` → `{ title, path }` → partial) is unchanged.
- **Relative URLs work naturally.** With microdata, `itemprop="item"` is carried by the crumb's `<a href="...">`. That `href` is the same relative URL the plugin already produces (e.g. `../index.html`, `index.html`). Microdata consumers resolve the URL against the page's own URL, so the relative links that AkashaCMS emits are handled correctly without any change.

#### 2.3 Note on the previous `p-category` class

Earlier versions of the template put `class="p-category"` on each crumb link. `p-category` is a **microformats2** property intended to mark a *tag / category / keyword* on an `h-entry` or `h-card` — it is not breadcrumb markup, and there was no `h-*` root wrapping the trail, so the classes were semantically inert. The `p-category` class was removed as part of adopting `BreadcrumbList`.

### 3. The JSON-LD Alternative (NOT Implemented)

Google's *recommended* format for breadcrumb structured data is **JSON-LD**: a `<script type="application/ld+json">` block describing the same `BreadcrumbList`. This section documents what such markup would look like, and why it has deliberately **not** been implemented in this plugin.

> **Status: NOT IMPLEMENTED.** The plugin does not emit JSON-LD. Only the inline microdata described in Section 2 is produced.

#### 3.1 What JSON-LD `BreadcrumbList` looks like

A JSON-LD breadcrumb block for a page three levels deep would look like:

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "BreadcrumbList",
  "itemListElement": [
    {
      "@type": "ListItem",
      "position": 1,
      "name": "Home",
      "item": "https://example.com/"
    },
    {
      "@type": "ListItem",
      "position": 2,
      "name": "Section",
      "item": "https://example.com/section/"
    },
    {
      "@type": "ListItem",
      "position": 3,
      "name": "Current Page",
      "item": "https://example.com/section/current.html"
    }
  ]
}
</script>
```

Each entry mirrors the microdata: a `ListItem` with a `position`, a `name`, and an `item` (the URL). For the last item, Google allows the `item` to be omitted (the current page), but the `name` and `position` are still required.

#### 3.2 Why JSON-LD is not used: it requires absolute URLs

The blocking reason is a mismatch between JSON-LD's requirements and AkashaCMS's rendering model:

- **JSON-LD `BreadcrumbList` requires absolute URLs.** In a JSON-LD block, `item` is a bare string (or an object) that is *not* attached to any element in the document. Because it is detached from the page DOM, there is no base element for a consumer to resolve a relative URL against reliably; Google's guidance and validators expect fully-qualified, absolute URLs (e.g. `https://example.com/section/`) for the `item` values.
- **AkashaCMS projects are rendered for relative URLs.** AkashaCMS renders sites using relative links between pages (e.g. `../index.html`, `index.html`) so that the output can be hosted from any base path or previewed from the local filesystem without a fixed origin. The breadcrumb plugin's crumbs carry exactly these relative paths (source: [../../../akashacms-breadcrumbs/index.mjs](../../../akashacms-breadcrumbs/index.mjs)).

Emitting correct JSON-LD would therefore require converting every relative crumb path into an absolute URL. That means:

- Reliably knowing the site's root/origin URL at render time (`config.rootURL` / `config.root_url`), and
- Computing the absolute URL for each crumb from the current document's render path plus the crumb's relative path.

This is exactly the kind of absolute-URL construction that the sitemap generator already performs, where each entry's `<loc>` is built from `config.root_url` plus the document's `renderPath` (see [Sitemap Validation Architecture](./sitemap-validation.md)). By contrast, the inline microdata approach sidesteps the whole problem: the crumb's own relative `href` serves as `itemprop="item"`, and the consumer resolves it against the page URL.

Because the relative-URL rendering model is a core AkashaCMS principle and the microdata approach already satisfies search engines without absolute URLs, JSON-LD was judged not worth the added complexity.

#### 3.3 What a future JSON-LD implementation would need

If JSON-LD support is added later, the design would need to:

1. Obtain the site origin from the configuration (`config.rootURL` / `config.root_url`), and fail gracefully (skip JSON-LD) when no root URL is configured.
2. Resolve each crumb's relative `path` to an absolute URL, using the current document's render path as the base (the same absolute-URL construction pattern used by the sitemap generator).
3. Build the `BreadcrumbList` object and serialize it into a `<script type="application/ld+json">` block, most likely injected into the page `<head>` rather than the visible trail.
4. Keep the JSON-LD in sync with the visible microdata trail (same names, same order, same positions) to avoid Google flagging a mismatch between structured data and visible content.
5. Ideally make JSON-LD opt-in via a plugin configuration flag, so sites that are genuinely deployed at a fixed origin can enable it, while relative-URL sites keep the microdata-only default.

### 4. Testing

The plugin's test suite verifies the emitted structured data by parsing the rendered HTML and asserting on the microdata attributes: the presence of the `BreadcrumbList` `itemtype`, the count of `a[itemprop="item"]` links, each link's relative `href`, and the sequential `meta[itemprop="position"]` values. These tests confirm the microdata is present and correctly numbered for trails of varying depth. (The breadcrumbs test suite lives in the `@akashacms/plugins-breadcrumbs` repository, which was migrated from Mocha/Chai to the Node.js built-in `node:test` runner as part of this work.)

### 5. Summary

- The breadcrumb trail emits **schema.org `BreadcrumbList`** as **inline microdata** on the existing links (`itemscope`/`itemprop`, with `ListItem`, `item`, `name`, and `position`).
- Microdata was chosen because it reuses the visible DOM and, crucially, works with the **relative URLs** AkashaCMS renders — the crumb's own `href` is the `item`.
- **JSON-LD is documented but intentionally not implemented**, because JSON-LD `BreadcrumbList` requires **absolute URLs**, which conflicts with AkashaCMS's relative-URL rendering model. Adding JSON-LD would require absolute-URL construction (as the sitemap generator does) and is best left as an opt-in future enhancement.
